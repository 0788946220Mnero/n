# نظام الولاء والمحفظة الرقمية — ديار الأنباط

نقاط على كل طلب مدفوع، ومكافآت تُستبدل عند الكاشير، وبطاقة ولاء في **Apple Wallet** و**Google Wallet** يتحدّث رصيدها تلقائياً.

المكوّنات:
- الخادم: هذا المستودع (Node/Express/MongoDB على سيرفر ميرو السحابي).
- لوحة التحكم: قسم «الولاء والمحفظة» وزر «الولاء» في «بيع سفري».
- الموقع: صفحة `wallet.html` (رابطها نجمة ⭐ في أعلى الموقع).

---

## 1) مسار النقاط

| الحدث | ماذا يحدث | مفتاح منع التكرار (`idemKey`) |
|---|---|---|
| بيع كاشير (سفري) مع عضو | يُكسب فوراً بعد إنشاء الفاتورة، لأن بيع الكاشير مدفوع لحظة البيع | `earn:<orderId>` |
| طلب موقع/تطبيق/سنتر | يُكسب عند «تم التسليم» فقط (الدفع عند الاستلام). يُنشأ العضو تلقائياً من رقم هاتف الطلب | `earn:<orderId>` |
| استبدال مكافأة عند الكاشير | يُخصم قبل إنشاء الفاتورة بشرط ذرّي `balance >= cost`. إن فشل إنشاء الفاتورة تُرجع النقاط فوراً | `redeem:<clientRef>` |
| إلغاء طلب كُسبت نقاطه | تُسحب نقاطه | `reverse_earn:<orderId>` |
| إلغاء فاتورة فيها استبدال | تُرجع النقاط المستبدلة | `reverse_redeem:<orderId>` |
| تعديل يدوي من الإدارة | سبب إلزامي، ويُسجَّل باسم المستخدم في «سجل المستخدم» | `adjust:<uuid>` |

**السجل `LoyaltyTransaction` هو المرجع الأساسي.** الرصيد في `LoyaltyAccount.balance` نسخة سريعة منه. زر «إعادة الحساب من السجل» في لوحة الإدارة يعيد بناءه من السجل.

القواعد المضمونة في الخادم، ولكل منها اختبار:
- **لا نقاط مرتين:** فهرس فريد على `idemKey`. إعادة الإرسال وإعادة المحاولة والطلبات المتزامنة كلها تنتج معاملة واحدة.
- **لا نقاط لطلب غير مدفوع أو ملغى:** طلبات الموقع لا تكسب قبل `delivered`، والملغى قبل الدفع لا يُنشئ أي معاملة.
- **لا استبدال أكبر من الرصيد:** الخصم بتحديث ذرّي مشروط (`$inc` مع `balance: {$gte: cost}`). الرفض يرجع 409، وفي هذه الحالة لا فاتورة ولا خصم ولا معاملة.
- **الرصيد لا يأتي من الواجهة:** الكاشير يرسل المعرّف (رمز البطاقة أو الهاتف) ورقم المكافأة فقط. الأسعار والخصم والنقاط كلها تُحسب في الخادم من قاعدة البيانات.
- **المعاملات:** تُستخدم معاملات MongoDB (`session.withTransaction`) حين يدعمها الخادم، وهي مدعومة على Atlas وأي Replica Set. على خادم منفرد بلا Replica Set يعمل النظام دون معاملات، وتبقى الضمانات قائمة على الفهرس الفريد والتحديث الذرّي المشروط.

### التقريب
- `fils = round(amount × 1000)` ثم `points = floor(fils × earnPerJod / 1000)`، أي **للأسفل دائماً**، وبلا أخطاء الفاصلة العائمة (3 د.أ = 30 نقطة بالضبط).
- مثال: 10.750 د.أ × 10 = **107** نقطة، لا 108.
- أساس الكسب = قيمة الأصناف − الخصم، وأجرة التوصيل تُضاف فقط إن فُعّل «احتساب أجرة التوصيل». معنى ذلك أن الفاتورة التي فيها استبدال تكسب على المبلغ المدفوع فعلاً.

### الاسترداد والإلغاء
- الإلغاء بعد الدفع يُعامل كاسترداد كامل: تُسحب نقاط الطلب وتُرجع النقاط المستبدلة فيه. كل ذلك مرة واحدة.
- **سياسة موثّقة:** إذا كان الزبون قد صرف النقاط قبل الإلغاء، يصبح رصيده **سالباً**، ويُسد من مشترياته القادمة. لا يمكن الاستبدال برصيد سالب.
- لا يوجد «استرداد جزئي» في النظام الحالي. الإلغاء للمدير فقط، كما كان.

### المكافآت
- `amount`: خصم مبلغ ثابت، بحد أقصى قيمة الفاتورة.
- `free_item`: صنف مجاني بسعره الأساسي (قطعة واحدة بلا إضافات)، ويجب أن يكون الصنف في السلة.
- الافتراضي عند أول تشغيل: «خصم دينار» = 1000 نقطة، أي 1% استرداد عند 10 نقاط/دينار.

لا شيء منها في الواجهة. لوحة الإدارة تعرض **أسماء** الناقص فقط.

| المتغير | مطلوب لـ | الوصف |
|---|---|---|

| `APPLE_PASS_TYPE_ID` | Apple | مثل `pass.com.diyaralanbat.loyalty` |
| `APPLE_TEAM_ID` | Apple | من صفحة Membership في حساب المطوّر |
| `APPLE_PASS_CERT_PEM_B64` + `APPLE_PASS_KEY_PEM_B64` | Apple | الشهادة والمفتاح بصيغة PEM ثم Base64 |
| `APPLE_PASS_KEY_PASSPHRASE` | اختياري | إن كان المفتاح مشفّراً |
| `APPLE_PASS_P12_B64` + `APPLE_PASS_P12_PASSWORD` | بديل | ملف ‎.p12 بدل PEM |
| `APPLE_WWDR_PEM_B64` | Apple | الشهادة الوسيطة WWDR التي وقّعت شهادتك (G4 عادةً) |
| `APPLE_PASS_AUTH_SECRET` | Apple | سر عشوائي (32 حرفاً على الأقل). منه يُشتق رمز كل بطاقة |
| `APPLE_APNS_HOST` | اختياري | الافتراضي `api.push.apple.com` |
| `GOOGLE_WALLET_ISSUER_ID` | Google | من Google Pay & Wallet Console |
| `GOOGLE_WALLET_SA_JSON_B64` | Google | ملف مفتاح حساب الخدمة (JSON) بصيغة Base64 |
| `GOOGLE_WALLET_SA_EMAIL` + `GOOGLE_WALLET_SA_PRIVATE_KEY_B64` | بديل | بدل ملف JSON |
| `GOOGLE_WALLET_CLASS_SUFFIX` | اختياري | الافتراضي `diyar_loyalty` |
| `GOOGLE_WALLET_ORIGINS` | مستحسن | نطاقات الموقع: `https://diyaralanbat.com,https://www.diyaralanbat.com` |
| `LOYALTY_MEMBER_PREFIX` | اختياري | بادئة رقم العضوية (الافتراضي `DY` ← `DY-000123`) |

## 3) التثبيت والتشغيل والاختبار

```bash
# الخادم
npm install                      # أُضيف: node-forge (توقيع Apple)، qrcode (رمز البطاقة)
npm start
npm test                         # كل الاختبارات (node:test)، ومنها tests/loyalty.test.js
node --test tests/loyalty.test.js
```

الاختبارات العشرة في `tests/loyalty.test.js` تعمل على المسارات الحقيقية وعلى قاعدة في الذاكرة فيها الفهارس الفريدة والتحقق:
1. الكسب بعد الدفع والتقريب للأسفل.
2. لا نقاط مرتين (إعادة الإرسال، إعادة المحاولة، التزامن).
3. رفض الاستبدال برصيد غير كافٍ بلا فاتورة ولا خصم.
4. عزل الزبائن والصلاحيات.
5. التعديل اليدوي وتسجيله.
6. الإلغاء والاسترداد.
7. Apple: ملف ‎.pkpass موقّع يُتحقق منه بـ `openssl smime -verify`، مع Web Service وAPNs.
8. Google: الصنف والبطاقة وJWT الحفظ RS256 وتحديث الرصيد.
9. أعطال Apple/Google لا توقف الكاشير.
10. البيع بلا ولاء كما كان تماماً.

النشر: الخادم على سيرفر ميرو السحابي (ادفع إلى GitHub فيُنشر)، واللوحة والموقع على Netlify (اسحب المجلد). إصدار اللوحة **v68**.

## 4) إعداد Apple Wallet من الصفر

يتطلب **حساب Apple Developer Program مدفوعاً** (99$ سنوياً).

1. **Pass Type ID:** من developer.apple.com ← Certificates, Identifiers & Profiles ← Identifiers ← ‎+‎ ← **Pass Type IDs**. الوصف «Diyar Loyalty»، والمعرّف `pass.com.diyaralanbat.loyalty`.
2. **طلب الشهادة (CSR):** على أي جهاز فيه OpenSSL، مثل جهاز الكاشير عبر Git Bash أو PowerShell مع OpenSSL:
   ```bash
   openssl req -new -newkey rsa:2048 -nodes -keyout pass.key -out pass.csr -subj "/CN=Diyar Loyalty/C=JO"
   ```
3. **الشهادة:** افتح الـ Pass Type ID ← Create Certificate ← ارفع `pass.csr` ← نزّل `pass.cer`، ثم:
   ```bash
   openssl x509 -inform DER -in pass.cer -out pass.pem
   openssl x509 -in pass.pem -noout -issuer -enddate   # الجهة المُصدِرة (WWDR G4 عادةً) وتاريخ الانتهاء
   ```
4. **WWDR:** من https://www.apple.com/certificateauthority/ نزّل الشهادة الوسيطة المطابقة للجهة المُصدِرة (Worldwide Developer Relations – G4)، ثم:
   ```bash
   openssl x509 -inform DER -in AppleWWDRCAG4.cer -out wwdr.pem
   ```
5. **Base64** (سطر واحد بلا فواصل):
   ```bash
   base64 -w0 pass.pem    # → APPLE_PASS_CERT_PEM_B64
   base64 -w0 pass.key    # → APPLE_PASS_KEY_PEM_B64
   base64 -w0 wwdr.pem    # → APPLE_WWDR_PEM_B64
   openssl rand -hex 32   # → APPLE_PASS_AUTH_SECRET
   ```
   في PowerShell: `[Convert]::ToBase64String([IO.File]::ReadAllBytes("pass.pem"))`.
6. **Team ID:** من صفحة Membership، ويُوضع في `APPLE_TEAM_ID`.
7. ضع المتغيرات في سيرفر ميرو السحابي مع `PUBLIC_API_URL` و`APPLE_PASS_TYPE_ID`، ثم أعد النشر.
8. في لوحة التحكم ← الولاء والمحفظة ← **Apple / Google**: يجب أن تظهر «جاهز» مع تاريخ انتهاء الشهادة.
9. **احفظ `pass.key` في مكان آمن ولا ترفعه لأي مستودع.** الشهادة صالحة سنة واحدة. اللوحة تنبّه قبل الانتهاء بـ 30 يوماً، والتجديد بإعادة الخطوات 2–5 لنفس الـ Pass Type ID.

كيف يعمل التحديث: البطاقة تحمل `webServiceURL = PUBLIC_API_URL/api/loyalty/apple`، وتسجّل الجهاز عند الإضافة. عند تغيّر الرصيد يرسل الخادم إشعار APNs فارغاً بشهادة البطاقة نفسها، فيطلب الهاتف آخر نسخة. لهذا الحالة «مضافة» تعني أن جهازاً سجّل البطاقة فعلاً.

## 5) إعداد Google Wallet من الصفر

1. **حساب المُصدِر:** https://pay.google.com/business/console ← أنشئ حساب Google Wallet API. خذ **Issuer ID** وضعه في `GOOGLE_WALLET_ISSUER_ID`.
2. **مشروع Google Cloud:** console.cloud.google.com ← مشروع جديد ← APIs & Services ← فعّل **Google Wallet API**.
3. **حساب خدمة:** IAM & Admin ← Service Accounts ← Create (بلا أدوار) ← Keys ← Add key ← JSON ← نزّل الملف.
4. **ربطه بالمُصدِر:** في Wallet Console ← Users ← Invite ← بريد حساب الخدمة (`…@….iam.gserviceaccount.com`) بصلاحية **Developer**.
5. **Base64:** `base64 -w0 key.json` ← `GOOGLE_WALLET_SA_JSON_B64`. وضع `GOOGLE_WALLET_ORIGINS` بنطاقات الموقع.
6. **الشعار:** Google يشترط شعاراً عبر https. يُؤخذ من «القواعد والبطاقة ← رابط الشعار»، أو من شعار المطعم في الإعدادات إن كان رابط https.
7. **وضع التجربة (Demo):** حساب المُصدِر الجديد في وضع تجربة، ولا يحفظ البطاقة إلا **حسابات Google المضافة كمختبِرين** في Wallet Console. للإطلاق للجميع: Wallet Console ← **Request publishing access** وأرفق لقطات البطاقة. الموافقة من Google وتستغرق أياماً.
8. في اللوحة ← Apple / Google: يجب أن تظهر «جاهز».

كيف يعمل التحديث: الخادم ينشئ صنف البطاقة (Class) والبطاقة (Object) عبر REST، وعند تغيّر الرصيد يرسل PATCH. إن تعذّر الوصول لـ Google لحظة الحفظ، يُرسل الرابط ببطاقة كاملة داخل الـ JWT فينشئها Google عند الحفظ، ويُحدَّث رصيدها في التغيير القادم.

## 6) الاختبار على هاتف حقيقي

**قبل الشهادات**، ويمكن ذلك اليوم:
1. افتح الموقع ← ⭐ ← سجّل برقمك (OTP). تظهر البطاقة ورمز QR، وأزرار المحفظة «غير مفعّلة بعد».
2. على الكاشير (بيع سفري): أضف أصنافاً ← **الولاء** ← اكتب رقمك أو امسح الرمز من شاشة هاتفك بقارئ الباركود (أو بالكاميرا على الجوال) ← تأكيد البيع. يظهر «+N نقطة».
3. حدّث صفحة ⭐ على هاتفك: الرصيد والسجل.
4. لوحة التحكم ← الولاء والمحفظة ← ابحث برقمك ← أضف 1000 نقطة بسبب ← بيع جديد ← الولاء ← اختر «خصم دينار». يظهر سطر الخصم في السلة والفاتورة.
5. ألغِ الفاتورة من «مبيعات السفري» (مدير). ترجع النقاط المستبدلة وتُسحب المكتسبة.

**Apple (بعد ضبط المتغيرات):**
1. على iPhone عبر **Safari**: ⭐ ← «أضف إلى Apple Wallet». تظهر معاينة البطاقة ← «إضافة».
2. ارجع للصفحة: الحالة «مضافة إلى المحفظة» (سجّل الجهاز).
3. بيع جديد على الكاشير. خلال ثوانٍ يتغيّر الرصيد على البطاقة ويظهر إشعار. إن لم يتغيّر: Wallet ← البطاقة ← ⋯ ← اسحب للتحديث، وراجع «آخر أخطاء التحديث» في اللوحة.
4. إن رفض iPhone الملف («Safari cannot download this file» أو «Invalid pass»): غالباً WWDR لا يطابق الجهة المُصدِرة، أو `APPLE_TEAM_ID` أو `APPLE_PASS_TYPE_ID` لا يطابقان الشهادة.

**Google (بعد ضبط المتغيرات):**
1. على Android عبر Chrome، وبحساب Google مضاف كمختبِر ما دام المُصدِر في وضع التجربة: ⭐ ← «أضف إلى Google Wallet» ← «حفظ».
2. ارجع للصفحة: «مضافة إلى المحفظة» حين يؤكد Google.
3. بيع جديد. يتحدّث الرصيد على البطاقة، وقد يتأخر دقائق من جهة Google.

## 7) ما اكتمل وما ينتظر جهات خارجية

**مكتمل ومُختبَر آلياً:**
- النماذج والفهارس الفريدة، والسجل كمرجع، والمعاملات.
- الكسب، والاستبدال، والإلغاء والاسترداد، والتعديل اليدوي، وإعادة الحساب.
- الصلاحيات: `loyalty:use` للكاشير والمشرف، و`loyalty:manage` للمشرف والمدير. وتظهر تلقائياً في شاشة المستخدمين.
- الكاشير (بيع سفري): البحث بالهاتف أو رمز QR (قارئ USB أو كاميرا)، والتسجيل، والرصيد، والمكافآت، وسطر الخصم، والإشعار، والفاتورة المطبوعة.
- قسم الإدارة: الأعضاء والسجل والتعديل، والمكافآت، والقواعد وألوان البطاقة، وحالة Apple/Google وأخطاؤها.
- صفحة الزبون `wallet.html`.
- توليد ‎.pkpass موقّع، ويُتحقق منه بـ OpenSSL في الاختبارات، مع Web Service الخاص بـ Apple وإشعارات APNs.
- Google: Class وObject وJWT الحفظ والتحديث.

**ينتظر جهات خارجية، ولم يُجرَّب على هاتف حقيقي بعد:**
- شهادة Apple Pass Type ID من حسابك في Apple Developer. **لم تُضف أي بطاقة إلى Apple Wallet فعلياً حتى الآن**، فالاختبارات استخدمت شهادات تجريبية مولّدة محلياً.
- حساب مُصدِر Google Wallet، وموافقة Google على النشر للعموم (Publishing access).
- الأزرار في صفحة الزبون بتصميم مبسّط. قبل الإطلاق العام يُستحسن استبدالها بالشارات الرسمية «Add to Apple Wallet» و«Add to Google Wallet» من موقعي Apple وGoogle، وفق إرشاداتهما.

**حدود معروفة:**
- شاشة DiyarPOS الاحتياطية بلا إنترنت (C#) لا تعرف الولاء. البيع بلا إنترنت يُزامَن لاحقاً بلا نقاط، ويمكن إضافتها يدوياً من اللوحة مع السبب.
- «بيع سنتر» يكسب نقاطاً عند التسليم برقم هاتف الطلب، لكن الاستبدال في السنتر غير مفعّل (الاستبدال من شاشة السفري فقط).
